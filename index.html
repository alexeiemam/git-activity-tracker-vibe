Run inside your repository. This uses up to three bounded Heroku Release List pages per environment (up to 3,000 events; later pages require the authenticated Heroku API and Python 3). It fetches tags from origin, adds GitHub Releases via gh, independently captures up to 3,000 Heroku releases each from remotes STAG, BETA and PROD (when authenticated), and copies authored history without a committer-date cutoff. It also checks up to 18 deployment SHAs against local Git objects and imports at most 175 additional commits per missing branch tip. To opt into at most four bounded GitHub fetches for unavailable SHA objects, run export GIT_SIGNALS_FETCH_DEPLOYMENT_SHAS=1 before the command. These fetches may update local shallow-repository metadata; failure leaves deployment evidence explicitly unresolved. No credentials or Heroku config values are requested; the imported release metadata and Git history stay in your browser. Incomplete Heroku access is reported per environment. The command uses macOS pbcopy; on other systems, remove the final pipe and copy terminal output.

For GitHub-published releases, the publication timestamp locates the event and the publisher is an assumed release driver; the publisher is not proof of who deployed. Lightweight Git tags have no tagger identity. Publishers are automatically linked only when imported Git identities give an unambiguous exact match; manual assignments override inference. The date scope is shared: contribution counts use authored dates, while release events use GitHub publication dates when available (otherwise annotated-tag or tagged-commit dates). Tagged release contents are reconstructed from the Git ancestry graph, independent of merge commits or VERSION changes. File revisitation, test accompaniment, codebase breadth and commit-subject categories are proxies, not proof of value, production deployment, code quality or hours worked.
